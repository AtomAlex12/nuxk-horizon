# nuxk Horizon — установка и проверка по шагам

| Где | Что | Как ставится |
|---|---|---|
| **Роутер Keenetic** | агент `nuxk-core`: nfqws2, WARP и VLESS (по желанию), списки DPI / WARP / VLESS, лёгкий веб `:4141` | `nuxk-lite.sh` на роутере |
| **Raspberry Pi** (необязательно) | контроллер: полный веб `:4200`, час истории графиков, подбор стратегий | `nuxk-full.sh` на Pi |
| между ними | `nuxk-core/api/openapi.yaml` — REST + события SSE; человек входит по паролю, контроллер — по ключу роутера | — |

Роутер работает и без Pi: списки и намерения хранятся на нём. Оба установщика ничего не
собирают — берут готовые файлы из релиза на GitHub и сверяют каждый с `SHA256SUMS`.

Ставьте **по этапам**: на каждом есть проверка и откат, следующий — только если
предыдущий в порядке. До этапа 5 nuxk **не меняет маршрутизацию** роутера.

---

## Этап 0. Подготовка роутера (один раз)

1. **Резервная копия конфигурации Keenetic.** «Управление → Параметры системы →
   Файлы» → скачайте `startup-config`. Это откат на крайний случай.
2. **Компоненты** («Управление → Параметры системы → Изменить набор компонентов»),
   роутер перезагрузится:
   - «Поддержка открытых пакетов OPKG»;
   - «Модули ядра подсистемы Netfilter» — без них nfqws2 не запустится;
   - «Протокол IPv6».
3. **Entware** — по [инструкции Keenetic](https://help.keenetic.com/hc/ru/articles/360021214160),
   на USB (ext4) или во внутреннюю память. SSH Entware: по умолчанию порт **222**,
   `root` / `keenetic`.
4. **Смените пароль Entware**: `ssh root@<роутер> -p <порт>` → `passwd`. Этим же паролем
   вы будете входить в панель nuxk.
5. **Время**: «Дата и время» → синхронизация (NTP) — без неё не работает HTTPS.

## Этап 1. nuxk на роутере (лайт)

В SSH-сессии Entware:

```sh
opkg update && opkg install curl ca-certificates
curl -fsSLo /opt/tmp/nuxk-lite.sh https://github.com/AtomAlex12/nuxk-horizon/releases/latest/download/nuxk-lite.sh
sh /opt/tmp/nuxk-lite.sh
```

Есть Pi? Можно ставить оттуда — см. этап 2, он делает то же самое по SSH.

Установщик сначала только смотрит (Entware, архитектура, место, модули ядра), потом
показывает план и спрашивает:

- **nfqws2-keenetic** — основа nuxk, ставится из его репозитория. **Внимание:** штатный
  nfqws2 сразу обрабатывает трафик по своему конфигу; если что-то перестало открываться —
  `/opt/etc/init.d/S51nfqws2 stop`;
- **WARP (usque) — по желанию.** «Да» = согласие с условиями Cloudflare WARP, создание
  интерфейса OpkgTun и сохранение конфигурации роутера; `cloudflareclient.com` заранее
  добавляется в список nfqws2 (ваши записи остаются);
- **VLESS (xray) — по желанию**, см. этап 6.

Дальше — агент, веб, адаптеры, `nuxk.conf` (0600: адрес только в LAN, ключ для
контроллера, **режим плана** `PLANE_APPLY="0"`), запуск и проверка. Каждый файл сверяется
с `SHA256SUMS` релиза; подменённый — установка останавливается, ничего не записав.

При первом запуске текущий `user.list` nfqws2 переносится в список «DPI» nuxk — ничего
не теряется.

**Проверка этапа:**
- `http://<роутер>:4141` → `root` и пароль Entware → «Дашборд»: в шапке «Роутер …»,
  графики WAN через 10–20 секунд, карточка nfqws2 «работает» (или «частично» — причина
  написана под карточкой, по каждому сайту — на странице nfqws2).
- После 5 неверных паролей подряд вход с этого адреса ненадолго блокируется (от 30 с,
  растёт до 15 мин) — защита от подбора.
- На роутере: `nuxk` — состояние; лог — `tail -f /opt/var/log/nuxk-core.log`.
- Интернет у всех устройств работает как раньше.

**Откат этапа:** `/opt/etc/init.d/S99nuxk-core stop` — роутер работает как до установки
(плюс штатный nfqws2: `S51nfqws2 stop`). Совсем — `nuxk uninstall`.

## Этап 2. Контроллер на Pi (фул, необязательно)

Нужен 64-битный Linux с Docker — Raspberry Pi 4/5 с 64-bit OS или любой x86_64
([get.docker.com](https://get.docker.com)). На Pi:

```sh
curl -fsSLo nuxk-full.sh https://github.com/AtomAlex12/nuxk-horizon/releases/latest/download/nuxk-full.sh
sh nuxk-full.sh
```

Скрипт запускает контроллер из готового образа `ghcr.io/atomalex12/nuxk-horizon-controller`
(в `~/nuxk/docker-compose.yml`) и предлагает поставить или обновить nuxk на роутере — по
SSH: адрес роутера, порт, пароль Entware вы вводите самому ssh, скрипт его не видит. На
роутере выполняется установщик лайт из того же релиза, с проверкой его хеша.

Откройте **http://<pi>:4200** — мастер настройки:

1. **Пароль** администратора панели (логин `admin`, не короче 8 символов). На Pi
   хранится только его хеш.
2. **Роутер** — его адрес, `root` и пароль Entware. Роутер выдаёт контроллеру свой ключ
   доступа; сам пароль нигде не сохраняется.
3. **Готово** — модель роутера и версия nuxk-core → «Открыть панель».

> Мастер открыт для первого, кто зайдёт на свежий контроллер: пройдите его сразу после
> установки.

В «Системе» — «через контроллер Pi»; графики хранят час истории. Там же «Сменить роутер»
и «Выйти». Забыли пароль администратора — удалите данные контроллера и пройдите мастер
заново: `sh nuxk-full.sh uninstall --purge && sh nuxk-full.sh`.

## Этап 3. Подбор стратегий (плагин GP, фул)

«Плагины» → GP → «Установить». Контроллер скачает на Pi ядро GP, Python-зависимости и
zapret2 (около минуты), запустит его отдельным процессом с сетевыми правами только внутри
контейнера и сменит его заводской пароль. Потом:

- **«Прогоны»** — выберите домены (список nuxk или свои), глубину («быстро» — до первой
  рабочей стратегии) и что проверять. Прогон может идти часами; найденное сохраняется.
- **«Стратегии»** — что нашлось. «На роутер…» покажет, что изменится, и после
  подтверждения добавит стратегию профилем nfqws2 только для выбранных доменов
  (`NFQWS_ARGS_CUSTOM`, копия `nfqws2.conf.nuxk-bak`, перезапуск nfqws2 на 1–2 с; если
  он не поднимется — конфиг вернётся сам). «Убрать» — обратно.

> Проверка идёт с Pi через роутер. Для доменов, уже стоящих в списке DPI, nfqws2 роутера
> накладывает свою стратегию на проверяемую — для точных результатов исключите Pi из
> nfqws2: политика подключения Keenetic с именем `nfqws` и `POLICY_EXCLUDE=1` в
> `/opt/etc/nfqws2/nfqws2.conf` (это изменение роутера — вручную).

## Этап 4. Списки в режиме плана

«Списки»: DPI / WARP / VLESS. Можно импортировать ваши списки Keenetic («Ваши списки в
Keenetic»). Сохраните и посмотрите блок «План»: что nuxk сделал бы на роутере. В режиме
плана **ничего не меняется**.

- Домены, которые ещё есть в ваших старых списках Keenetic, стоят в «Конфликтах» — nuxk
  их не трогает, пока вы не уберёте их из старого списка.
- «Туннель упал: напрямую / блокировать» — что делать с сайтами WARP/VLESS при падении
  туннеля. Режим «блокировать» на железе ещё не проверен — начните с «напрямую».

## Этап 5. Применение — начните с одного домена

1. Оставьте в «Списках» **один** тестовый домен (например, в WARP).
2. На роутере: `PLANE_APPLY="1"` в `/opt/etc/nuxk/nuxk.conf`, затем
   `/opt/etc/init.d/S99nuxk-core restart`.
3. Через минуту в «Списках» → «Роутер»: «применяется», план пуст, ошибок нет. В
   веб-интерфейсе Keenetic появится список `nuxk-warp` с маршрутом.
4. Откройте домен с устройства; выход — через WARP
   (`https://www.cloudflare.com/cdn-cgi/trace` показывает `warp=on`).
5. Только потом переносите остальные домены.

**Откат этапа 5** (в порядке строгости):
- удалите списки в «Списках» и сохраните — nuxk сам уберёт свои `nuxk-*` объекты;
- `PLANE_APPLY="0"` + рестарт — nuxk перестаёт менять роутер;
- `nuxk uninstall` — убирает и объекты `nuxk-*`. Ваши собственные списки и маршруты nuxk
  не трогает никогда; свои объекты он не сохраняет в конфигурацию роутера, так что после
  перезагрузки без nuxk их тоже нет.

## Этап 6. VLESS через xray (по желанию)

Для сайтов, которые nfqws2 не открывает — их блокируют по IP (так пишет проба nfqws2:
«не соединяется — похоже, блокировка по IP»), — или которые надо увести с вашего адреса.
Нужен свой сервер VLESS — например, 3x-ui.

1. **На роутере:** `nuxk vless` (или «да» на вопрос про VLESS при установке). Установщик
   скачает xray — официальный релиз XTLS, со сверкой закреплённого хеша, — и положит на
   роутер только сам xray (≈35 МБ в `/opt`; на mips — soft-float сборка); создаст в
   Keenetic интерфейс — первый свободный начиная с OpkgTun1, с описанием `nuxk-vless`
   (чужие интерфейсы не трогает) — и сохранит конфигурацию роутера. Это изменение
   роутера: «да» — ваше согласие.
2. **Сервер.** xray проверит конфиг и запустится; если с новым сервером не поднимется —
   вернётся прежний.
   - **Лайт** — панель роутера → xray (VLESS) → «Сервер VLESS»: одна ссылка `vless://`
     (3x-ui: «Инбаунды» → клиент → «Поделиться») или одна подписка. У подписки видны
     трафик, срок и все её серверы — «Выбрать» переключает; роутер перечитывает её сам
     (по расписанию панели, обычно раз в 12 ч) и перезапускает xray, только если сервер
     изменился.
   - **Фул** — панель на Pi → xray (VLESS) → «Серверы VLESS на Pi»: сколько угодно
     ссылок и подписок, «На роутер» у нужного сервера. Роутер получает один сервер
     ссылкой; подписки перечитывает контроллер и сам присылает роутеру новые настройки
     сервера, если панель их сменила.
3. **Проверка:** карточка xray «работает», «Проба» — `ok` и выходной IP вашего сервера.
   В Keenetic у интерфейса `nuxk-vless` есть адрес `172.16.2.1` и он поднят.
4. **Списки → «VLESS»**: домены через сервер. В туннель они уходят, когда применение
   включено (этап 5); начните с одного домена.

IP сервера сам попадает в список nfqws2 (endpoints), так что рукопожатие Reality тоже
проходит через десинк.

> xray занимает 30–60 МБ памяти. На mips-роутерах с 128 МБ это ощутимо — если роутер
> начнёт тормозить, остановите xray в панели.

## Этап 7. Защищённый DNS (бета, по желанию)

Провайдер может подменять ответы DNS на заглушки, а маршрутизация по доменам отправляет в
туннель тот адрес, который ответил DNS. С защитой роутер спрашивает nuxk, а nuxk — серверы
DoH через туннель (VLESS, потом WARP, потом напрямую).

1. **Сначала проверка** — панель → «DNS» → «Проверка подмены» → «Проверить». Колонка
   «8.8.8.8 обычным DNS» покажет, подменяет ли провайдер; «роутер» — что получают устройства.
   Если у роутера уже «честно» (например, в Keenetic настроен DoH), защита — запас на случай,
   когда провайдер начнёт блокировать и DoH.
2. **Включить** — «Защищённый DNS» → «Включить». nuxk проверит, что серверы DoH отвечают,
   добавит себя в DNS-прокси Keenetic и проверит, что роутер по-прежнему отвечает на DNS; если
   нет — сразу уберёт себя обратно.
3. **Проверить:** «роутер спрашивает nuxk — да», счётчик вопросов растёт, в таблице путей
   отвечает VLESS или WARP. Повторите «Проверку подмены»: у роутера должно быть «честно».
4. **Кэш ответов** (с 0.5.0-beta.3, включён сам): nuxk запоминает ответы на время, которое
   разрешил сервер, заранее обновляет часто нужные и при сбое туннелей отдаёт последний
   известный адрес. DNS-прокси Keenetic тоже кэширует, поэтому доля ответов из кэша nuxk
   может быть небольшой — это нормально; главное — строка «выручил при сбое». Если что-то
   открывается странно — «Очистить» или снимите «запоминать».

**Откат этапа:** «Выключить» на том же экране. Вручную, по SSH на роутере:
`ndmc -c "no ip name-server 192.168.1.1:53053"` (адрес — ваш роутер в домашней сети, как в
«DNS» → «адрес nuxk») — запись живёт только в текущей
конфигурации, после перезагрузки её нет, пока nuxk не добавит снова (он добавляет, если
защита включена в панели).

> На устройствах со своим DNS («Частный DNS» на Android, «Безопасный DNS» в браузере, свой
> VPN) вопросы идут мимо роутера — на них защита не действует.

## Обновление

- **Роутер — кнопкой.** Раз в сутки роутер смотрит релизы на GitHub; когда выйдет
  новый, в шапке панели появится «доступна X». «Система» → «Обновления»: что нового и
  кнопка «Обновить». Панель показывает, как идёт обновление; агент перезапускается на
  10–30 с — обход и туннели в это время работают, вход сохраняется. Там же — выключить
  проверку или получать и бета-версии.
- **Роутер — по SSH:** `nuxk update` — то же самое: последний релиз, агент, веб, адаптеры
  (и xray, если его версия сменилась). `nuxk.conf` не трогается.
- **Pi:** `sh ~/nuxk/nuxk-full.sh update` — новый образ контроллера, затем (по вопросу)
  роутер. Контроллер кнопкой не обновляется: он в Docker и не может заменить свой
  контейнер; панель подскажет, когда он отстал от роутера.

Каждое обновление сначала проверяет **подпись релиза** — это делает агент, который уже
работает на роутере, до того как что-то поменять. Подменённый или неподписанный релиз
не встанет: `SHA256SUMS релиза не подписан ключом nuxk Horizon`.

**Если новая версия не запустилась** (не ответила за 15 с) — прежняя возвращается сама;
в панели будет «возвращена прежняя версия» и вывод обновления. Вернуть прежнюю вручную,
даже когда новая работает: `nuxk rollback` (агент, веб и адаптер nfqws2 до последнего
обновления лежат в `/opt/var/lib/nuxk/prev`; команда `nuxk` остаётся новой).

## Удаление

- **Роутер:** `nuxk uninstall` — агент, веб, адаптеры, объекты `nuxk-*`; конфиг и списки
  откладываются в `/opt/etc/nuxk.removed`. Спросит, убирать ли xray с его интерфейсом.
  WARP и nfqws2-keenetic — отдельно: `opkg remove usque-keenetic`,
  `opkg remove nfqws2-keenetic`.
- **Pi:** `sh nuxk-full.sh uninstall` (с данными — `--purge`).

## Что проверено до релиза и что нет

- **Проверено:** юнит-тесты и `-race`; установщик лайт — на имитации роутера под dash и
  busybox ash (подменённый файл, чистая установка, WARP и VLESS с чужим интерфейсом,
  повтор, обновление, удаление); плоскость на имитации RCI с реальными ответами
  прошивки; контракт OpenAPI против маршрутов агента; контроллер (прокси, ключи,
  история, SSE, падение агента); веб в браузере через агент и через контроллер,
  светлая/тёмная тема, телефон.
- **Подбор стратегий:** хост плагинов в контейнере контроллера (плагин не читает секреты
  контроллера и его память); настоящий прогон GP с Pi; применение, откат и «Убрать» —
  на настоящем агенте с имитацией nfqws2 и заводским `nfqws2.conf`.
- **VLESS:** официальный xray 26.3.27 и свой сервер VLESS + Reality (vision) на Pi —
  ссылка через API, туннель, смена сервера на ходу, проба через туннель.
- **Обновление кнопкой:** на Pi, на имитации роутера — настоящий агент, настоящий
  `nuxk-lite.sh`, подписанный релиз (тестовым ключом): обновление из лёгкой панели и
  через контроллер, вход после перезапуска сохраняется, «сломанный» релиз
  откатывается сам; подменённый и неподписанный релиз, релиз старше установленного,
  `nuxk rollback` — в тестах установщика.
- **На железе (Keenetic Ultra, 0.3.0):** списки DPI / WARP / VLESS с применением на
  роутере, xray со своим интерфейсом OpkgTun; сутки без сбоев. Поставлено ещё прежним
  веб-инсталлятором.
- **Не проверено на железе:** установщики `nuxk-lite.sh` / `nuxk-full.sh` и обновление
  кнопкой на настоящем роутере (первым будет 0.4.0 → следующий релиз), режим
  «блокировать», применение стратегии GP на роутере.

Если что-то упало — пришлите вывод установщика, `tail -50 /opt/var/log/nuxk-core.log` и
`cat /opt/var/log/nuxk-core.crash`.
